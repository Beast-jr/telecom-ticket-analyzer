## What this means

**Two kinds of score.** *Match* asks: "is our suggestion the same fix the agent actually recorded?" *Useful* asks: "ignoring what was recorded, would an experienced agent think this is a sensible, safe thing to try, knowing only what the customer wrote?" A suggestion can be very useful and still score low on match, for example checking the customer's router when the recorded cause turned out to be a fault at the exchange.

**Why match is capped on this data.** The tickets are synthetic: for each complaint the generator picked one plausible root cause at random (the same "gaming lag" complaint might be a routing loop in one ticket and cell congestion in another), and the customer's description usually doesn't reveal which. No system, and no human agent, can reliably guess a hidden, randomly chosen cause from the description alone, so a perfect match score is impossible here. The useful score is the better measure of whether the suggestions would actually help an agent.

**Results.** Retrieval found at least one past ticket from the right category for 96% of the 50 unseen tickets (the very first match was the right category 80% of the time), and a ticket with the exact same subtopic for 92%. Our #1 suggestion is often reasonable but not always the obvious first step (useful 3.86/5; best of 3: 4.58/5). Against the recorded resolution, #1 is often partly the recorded fix (match 3.36/5). The best of the 3 matches noticeably better (4.14/5), so the recorded fix is often among the options but not ranked first; ranking has room to improve. Higher suitability % goes with higher match and useful scores, so the % is a useful confidence signal. The judge saw the 3 options as genuinely different approaches 100% of the time.

## Method notes

- **Holdout never ingested:** the 50 holdout tickets were split off before embedding and are not in the vector store, so every ticket is new to the system.
- **The judge is an LLM** (openai/gpt-oss-120b), scoring match against the recorded resolution and usefulness from the description alone, in one call per ticket. It can be biased (e.g. toward fluent or longer answers, or answers from its own model family), so treat scores as indicative, not ground truth.
- **Small sample:** 50 tickets (about 6 per category). Differences of a few percentage points, especially per category, are within noise.
- **Synthetic data:** both the tickets and their "real" resolutions were generated by an LLM. The generated root cause often can't be inferred from the ticket text (e.g. a routing loop vs. congestion for the same lag complaint), so matching the exact fix is partly luck, and scores may not reflect real-world accuracy in either direction.
